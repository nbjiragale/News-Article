# ArthaReader — Production Readiness Review

**Reviewed commit:** `9d6a80d` (main) · **Branch:** `claude/production-readiness-review-e3w7o2`
**Scope:** entire repository — 54 Kotlin source files, ~8,900 LOC, single Gradle module.
**Stack:** Kotlin 2.0.21 · Jetpack Compose (BOM 2024.09.00) · Room 2.8.4 · KSP · `HttpURLConnection` · OpenRouter + Deepgram.

> **Status update.** This document is a point-in-time assessment of `9d6a80d`. Action-plan
> items **C1–C4 have since been fixed** (missing arrow drawables added, duplicate
> `AppTopBar`/`BottomSheetHandle` removed, CI workflow added, fabricated progress UI
> removed). The findings below are left as written so the analysis stays traceable; see
> §10.1 for which items are now closed. Everything from C5 onward is still open.

> This review assumes the goal stated in the README ("an Android app for contextual
> English learning") rather than the PRD's "single user, personal use, not publishing to
> Play Store". Where the two conflict, findings are graded against the README's ambition,
> and the gap is called out explicitly. If the PRD still governs, roughly half the
> Critical/High items collapse to Nice-to-have — see §10.5.

## 1. Overall Assessment

### 1.1 Current strengths

These are genuinely well done and should not be refactored away:

- **Domain layer is pure and testable.** `TextAnalysis.kt`, `ArticleFormatter.kt`,
  `MeaningResult.kt`, `CleanArticleResult.kt` are free of Android and framework types.
  This is why the five unit test files exist at all — the design earned them.
- **Interface-based seams at the right boundaries.** `ArticleAiService` and
  `ArticleLocalStore` are declared where they're consumed, and the concrete
  `OpenRouterArticleService` / `RoomArticleLocalStore` sit behind them. The ViewModel
  depends only on the abstractions. That is textbook dependency inversion, and it is
  the single best structural decision in the codebase.
- **Cancellation hygiene is above average.** Every `catch` in the ViewModel and in
  `retryWithBackoff` rethrows `CancellationException` before the generic handler. This
  is the #1 thing Android codebases get wrong with coroutines, and it is correct here.
- **Stale-response guarding.** `updateMeaningIfStillSelected` and the
  `current.cleanedArticle?.cleanArticle == displayResult.cleanArticle` checks prevent a
  slow in-flight response from clobbering newer state. Someone thought carefully about
  races.
- **Deepgram pipelining is genuinely sophisticated.** Launching all chunk syntheses
  up-front behind a `Semaphore(3)` and awaiting them in order so playback starts after
  chunk 1 rather than after chunk N is the right design. The binary search in
  `WordTimings.indexForPosition`, the LRU-ish disk cache with `.tmp`+rename atomic
  writes, and the versioned timings format (`TIMINGS_FORMAT_VERSION`) are all
  production-grade instincts.
- **Recomposition scoping in the reader.** Passing `currentWordIndex` as `null` to every
  paragraph except the active one (`ArticleViewerScreen.kt:249`) is a deliberate,
  correct optimisation that most Compose codebases miss.
- **Release-gated verbose logging.** `logDebug`/`logInfo` compiled out behind
  `BuildConfig.DEBUG` in both network services keeps content out of production logcat.

### 1.2 Biggest weaknesses

1. **The app does not compile.** Three separate defects, all introduced by the same commit
   (`cbc4380`, "Apply ArthaReader emerald redesign") and merged to `main` in `9d6a80d`:
   two drawables are referenced and do not exist (§2.1); two `@Composable` functions are
   declared twice in the same package (§2.2); and `Theme.kt` uses `Color(0xFF5C0B0B)`
   without importing `androidx.compose.ui.graphics.Color` (§2.2b). Nothing in the repo
   would have caught any of them — there is no CI.

   > The third was found by the compiler, not by this review — it surfaced on the first
   > green-path CI run. It is a fair illustration of the review's own limits: §2.4 quotes
   > that exact line while discussing dark mode and still did not check the file's
   > imports. Static reading is not a substitute for a build.
2. **API keys ship inside the APK.** `BuildConfig` string fields are plaintext constants
   in `classes.dex`. `isMinifyEnabled = false` for release. Anyone with `apktool` has
   your OpenRouter and Deepgram billing.
3. **Cost model is unbounded and untracked.** Every single word tap sends the *entire
   article* to the LLM, up to twice, each wrapped in three retries — up to six
   full-article requests per tap.
4. **The persistence layer leaks rows.** `saveRecentArticle` is a plain `@Insert` against
   an autogenerated primary key, and it is called on every summary generation. Reading
   one article and generating context produces duplicate rows forever. Nothing prunes
   anything.
5. **Fabricated UI.** Every card on the Recents screen renders a hardcoded `0.4f`
   progress bar and the literal text "40% read".
6. **No CI, no crash reporting, no signing config, no lint gate, no DI framework, and
   zero tests for the ViewModel, repository, or Room migrations.**

### 1.3 Scores

| Dimension | Score | Rationale |
|---|---|---|
| **Code quality** | **5 / 10** | Idiomatic Kotlin, good domain purity, thoughtful concurrency. Dragged down by duplicated composables, ~200 lines of dead code, 500-line files with five responsibilities, hardcoded finance-domain heuristics, and copy-pasted call sites. |
| **Production readiness** | **2 / 10** | Does not compile. Secrets in the binary. No CI, no crash reporting, no release signing, no minification. Data grows without bound. Placeholder UI shipped to users. |

The 2 is not harsh — a build that does not produce an artifact is definitionally not
production ready. Fixing §10.1 alone moves this to roughly 4; the full Critical + High
list moves it to 7.

## 2. Frontend Review (Compose)

### 2.1 🔴 CRITICAL — Missing drawable resources: the build fails

**Where:** `ui/components/AppTopBar.kt:49`, `ui/screens/ArticleInputScreen.kt:224`

```kotlin
// AppTopBar.kt:49
painter = painterResource(R.drawable.ic_arrow_left),
// ArticleInputScreen.kt:224
```

Neither `ic_arrow_left` nor `ic_arrow_right` exists anywhere under `app/src/main/res/`.

### 2.2 🔴 CRITICAL — `AppTopBar` and `BottomSheetHandle` are each declared twice

**Where:** `ui/components/AppTopBar.kt` and `ui/components/ArticleChrome.kt` — same
package, `com.niranjan.englisharticle.ui.components`.

```kotlin
// AppTopBar.kt:30
fun AppTopBar(showBack: Boolean = false, onBack: (() -> Unit)? = null,
              onRecentsClick: (() -> Unit)? = null, onSavedWordsClick: (() -> Unit)? = null,
              onPracticeClick: (() -> Unit)? = null, modifier: Modifier = Modifier)

// ArticleChrome.kt:45
fun AppTopBar(showBack: Boolean, onBack: () -> Unit = {},
              onRecentsClick: (() -> Unit)? = null, onSavedWordsClick: (() -> Unit)? = null,
              onPracticeClick: (() -> Unit)? = null)
```

`AppTopBar.kt` was created by the redesign commit `cbc4380`; `ArticleChrome.kt` has
carried an `AppTopBar` since `52be07e`. The redesign added a second implementation
instead of editing the first. Same story for `BottomSheetHandle` (`AppTopBar.kt:136`
vs `ArticleChrome.kt:241`).

**Why it's a problem:** Every call site — `ArticleInputScreen.kt:82`,
`ArticleViewerScreen.kt:197`, `PracticeScreen.kt:82`, `SavedWordsScreen.kt:56`,
`RecentArticlesScreen.kt:50` — supplies arguments that are applicable to *both*
overloads (`() -> Unit` satisfies both `onBack: () -> Unit` and `onBack: (() -> Unit)?`),
with both candidates relying on default arguments. That is an
`OVERLOAD_RESOLUTION_AMBIGUITY`.

**Impact:** Compilation failure at five call sites, and — even if the compiler happened
to disambiguate — two visually different top bars would be live simultaneously (one with
a `ಅ` circle + "ArthaReader" wordmark, one with a PNG logo + `stringResource(app_name)`).
That is also why §2.1's missing icon went unnoticed: the *other* `AppTopBar` uses
`ic_move_left`, which exists.

**Fix:** Delete the `AppTopBar` and `BottomSheetHandle` declarations from
`ArticleChrome.kt`, keeping only `ArticleHeader` there (rename the file to
`ArticleHeader.kt`). Keep the newer `AppTopBar.kt` as the single source of truth. Then
delete the no-op `Modifier.interactiveWordUnderline` (`ArticleChrome.kt:258`), which
returns `this` unchanged in both branches.

### 2.3 🔴 CRITICAL — Fabricated reading-progress UI

**Where:** `ui/screens/RecentArticlesScreen.kt:155-166`

```kotlin

// RecentArticleEntity

val readProgress: Float
```

### 2.4 🟠 HIGH — Dark mode is broken for every card and text field

**Where:** `ui/theme/Theme.kt:63-101`, `ui/theme/Color.kt:62`

`DarkColorScheme` sets `primary`, `surface`, `outline`, `error` — but never sets
`surfaceContainerLowest`, `surfaceContainerLow`, `surfaceContainer`,
`surfaceContainerHigh`, `surfaceContainerHighest`, `scrim`, `inverseSurface`, or
`inversePrimary`. The light scheme sets all of them.

`surfaceContainerLow` is the background of essentially every card in the app —
`MeaningInfoCard`, `SavedWordCard`, `RecentArticleCard`, `ArticleSummaryCard`, the input
card. In dark mode they all fall back to the Material 3 *baseline* dark palette, which is
purple-tinted, not emerald-tinted stone.

Worse, `ArticleInputScreen.kt:283-284` bypasses the theme entirely:

```kotlin
focusedContainerColor   = AppSurfaceContainerLowest,   // == Color(0xFFFFFFFF)
unfocusedContainerColor = AppSurfaceContainerLowest,
```

That is a hardcoded pure-white text field on a `Stone950` background, with

`Color(0xFFD3F1E2)` and `Color(0xFF1F9D6F)`.

```kotlin
// Color.kt — replace hardcoded practice-feedback colours
```

### 2.5 🟠 HIGH — The core interaction is invisible to screen readers

**Where:** `ui/screens/ArticleViewerScreen.kt:392-408`

```kotlin
Text(
    text = renderContent.text,
    modifier = Modifier
        .pointerInput(renderContent.ranges) {
            detectTapGestures(
                onTap      = { position -> openMeaning(position, showSentence = false) },
                onLongPress = { position -> openMeaning(position, showSentence = true) }
            )
        },
    ...
)
```

**Why it's a problem:** Raw `pointerInput` gestures carry no semantics. TalkBack sees a
single non-interactive text blob. There is no way to discover that words are tappable, no
way to focus an individual word, no way to trigger the long-press "sentence" mode, and no
announcement when the bottom sheet opens.

**Impact:** The app's entire reason for existing — tap a word, get a Kannada meaning — is
unusable with a screen reader. For a *language learning* app, whose users may also have
low vision, this is a serious exclusion. It also fails Play Store accessibility guidance.

**Fix:** Attach semantics with custom actions, and mirror the gesture:

```kotlin
Text(
    text = renderContent.text,
    modifier = Modifier
        .semantics {
            contentDescription = paragraphPlainText
            customActions = renderContent.ranges.map { range ->
                CustomAccessibilityAction("Meaning of ${range.lookupText}") {
                    onWordTap(SelectedWord(
                        word = range.lookupText,
                        sentence = articleBody.findSentenceContaining(range.sourceStartIndex),
                        showSentence = false
                    )); true
                }
            }
        }
        .pointerInput(renderContent.ranges) { /* unchanged */ },
)
```

Longer term, `ClickableText` / `LinkAnnotation` (Compose 1.7+) gives per-span
accessibility for free and is the right primitive here.

**Related accessibility gaps:**
- `SmallSpeakButton` (`MeaningSheet.kt:442-445`) and `ArticleSummaryCard.kt:194` are
  `Modifier.size(32.dp)` — below the 48dp minimum touch target. Use
  `Modifier.minimumInteractiveComponentSize()` or size to 48dp with a 18dp icon.
- No `LinearProgressIndicator` in the reader carries a `progressBarRangeInfo` semantic.
- `AppTopBar.kt:64` renders the logo as `Text("ಅ")` — announced as a Kannada letter.
  Wrap in `Modifier.clearAndSetSemantics {}`.

### 2.6 🟠 HIGH — Rotation destroys imported/shared articles and stops playback

**Two independent causes:**

**(a) Intent re-delivery.** `MainActivity.kt:23` calls `handleIncomingIntent(intent)` in
`onCreate`. On configuration change the Activity is recreated with the *same* intent,
`nextSharedArticleId` resets to `0`, a new `SharedArticleText(id = 1, ...)` is emitted,
and `EnglishLearningApp.kt:83`'s `LaunchedEffect` fires again — calling
`importSharedArticleText`, which does:

```kotlin
// EnglishLearningViewModel.kt:211
_uiState.value = EnglishLearningUiState(draftArticle = sharedArticle)
```

That is a **total state wipe**. Reproduction: share text into the app → open the article
→ rotate → the cleaned article, summary, and selection are gone.

**Fix:** Mark the intent consumed so it is not reprocessed:

```kotlin
private fun handleIncomingIntent(intent: Intent?) {
    if (intent == null || intent.getBooleanExtra(EXTRA_CONSUMED, false)) return
    val sharedText = intent.extractSharedArticleText(this)?.trim()
        ?.takeIf { it.isNotBlank() } ?: return
    intent.putExtra(EXTRA_CONSUMED, true)
    sharedArticleText.value = SharedArticleText(id = ++nextSharedArticleId, text = sharedText)
}
```

…and make `importSharedArticleText` non-destructive (`_uiState.update { it.copy(draftArticle = ...) }`).

**(b) Speaker lifetime.** `rememberArticleSpeaker()` (`ArticleSpeaker.kt:142-149`) ties
`ArticleSpeaker` to the composition with `DisposableEffect { onDispose { shutdown() } }`.
Activity recreation disposes the composition → `shutdown()` → `scope.cancel()` →
audio stops mid-article. Rotating the phone while listening kills playback.

**Fix:** Hoist `ArticleSpeaker` into the `ViewModel` (or a `MediaSessionService` for real
background playback — see §9.2), so it survives configuration changes and is released in
`onCleared()`.

### 2.7 🟡 MEDIUM — Word-count recomputed over the entire pasted article on every keystroke

**Where:** `ui/screens/ArticleInputScreen.kt:248`

```kotlin
val wordCount = article.trim().split(Regex("\\s+")).size
```

This is inside the composable body, so it runs on every recomposition — i.e. every
keystroke. For a pasted 50 KB article it allocates a ~9,000-element `List<String>` per
character typed, on the main thread.

**Fix:**

```kotlin
val wordCount by remember(article) {
    derivedStateOf { WORD_REGEX.findAll(article).count() }   // no list allocation
}
```

Better still, debounce: `snapshotFlow { article }.debounce(200).map { ... }`.

### 2.8 🟡 MEDIUM — Every paragraph's `AnnotatedString` is rebuilt on every word lookup

**Where:** `ui/screens/ArticleViewerScreen.kt:422-431`

`buildParagraphRenderContent` keys its `remember` on `lookedUpWords` (a `Set`). Tapping
any word produces a new set instance (`ArticleViewerScreen.kt:125`), invalidating the
`remember` for **every** paragraph, so all N paragraphs rebuild their `AnnotatedString`
and range lists.

**Fix:** Pass only the flag that this paragraph cares about. Compute per-paragraph
whether any of *its* tokens are in the looked-up set:

```kotlin
val paragraphLookedUp = remember(tokenGroups, lookedUpWords) {
    tokenGroups.mapTo(HashSet()) { it.cleanText().lowercase() }
        .intersect(lookedUpWords)          // small, stable per paragraph
}
```

Then `remember(paragraphLookedUp, ...)` only invalidates paragraphs that actually changed.

### 2.9 🟡 MEDIUM — Reading progress is quantised to whole paragraphs

**Where:** `ui/screens/ArticleViewerScreen.kt:148-155`

```kotlin
listState.firstVisibleItemIndex.toFloat() / (totalItems - 1).toFloat()
```

Progress jumps in discrete steps as paragraphs scroll past, and ignores scroll offset
within a paragraph. On a 6-paragraph article the bar moves in 20% jumps.

**Fix:** Fold in `firstVisibleItemScrollOffset` relative to the item's size:

```kotlin
val info = listState.layoutInfo
val first = info.visibleItemsInfo.firstOrNull() ?: return@derivedStateOf 0f
val within = if (first.size == 0) 0f else (-first.offset).toFloat() / first.size
((first.index + within) / (info.totalItemsCount - 1)).coerceIn(0f, 1f)
```

### 2.12 State management assessment

**Verdict: sound pattern, one structural flaw.**

The `MutableStateFlow<UiState>` + `asStateFlow()` + `update {}` pattern is correct and
consistently applied. Single source of truth, immutable data class, no `var` leakage.
Job handles are cancelled before restarts.

The flaw is that **`EnglishLearningUiState` is one god-object of 12 fields spanning four
unrelated concerns** — draft input, YouTube import, article cleaning, and word lookup.
Any change to `draftArticle` (every keystroke) emits a new state object that every
`collectAsState()` consumer sees, including the reader screen. Compose's structural
equality saves most recompositions, but the model is conceptually wrong.

**Fix:** Split into per-screen states, or at minimum separate the lookup:

```kotlin
data class InputUiState(
    val draftArticle: String = "", val isCleaningArticle: Boolean = false,
    val cleaningError: String? = null, val draftYouTubeUrl: String = "",
    val isImportingYouTube: Boolean = false, val youTubeError: String? = null,
)
data class ReaderUiState(
    val article: CleanArticleResult? = null,
    val isSummarizing: Boolean = false, val summaryError: String? = null,
)
data class LookupUiState(
    val selected: SelectedWord? = null,
    val meaning: MeaningUiState = MeaningUiState.Idle,
)
// expose three StateFlows; screens collect only what they need
```

Also: **navigation events use a zero-buffer `MutableSharedFlow`**
(`EnglishLearningViewModel.kt:57`). `MutableSharedFlow()` defaults to `replay = 0,
extraBufferCapacity = 0, onBufferOverflow = SUSPEND`, so `emit` **suspends until a
collector consumes it**. During Activity recreation there is a window with no collector —
the emit at `:176` / `:449` blocks, and the code *after* it (idiom extraction and
`saveRecentArticle`) never runs. The article silently fails to reach history.

**Fix:** `MutableSharedFlow(extraBufferCapacity = 1, onBufferOverflow = BufferOverflow.DROP_OLDEST)`,
or model navigation as consumable state in `EnglishLearningUiState`.

### 2.13 Reusability, error handling, loading states

- **Reusability: adequate.** `Expressive.kt` (`Pill`, `SkeletonBlock`, `EmptyState`,
  `SectionHeader`) is a real component library and is used across three screens. Good.
  `SectionHeader` and `SkeletonBlock` are only used once each — keep them, they're cheap.
- **Loading states: good.** Three distinct treatments (button spinner, skeleton shimmer,
  centred progress) appropriate to their contexts. `ArticleSummaryCard`'s skeleton is a
  nice touch.
- **Error handling: inconsistent.** Cleaning errors get an inline card with **Retry**;
  YouTube errors get **Dismiss** but *no* retry, even though the underlying failure
  (HTTP 429) is exactly what a retry is for. Meaning errors get a card with no action at
  all — the user must dismiss the sheet and re-tap the word. Summary errors appear in two
  places (`ArticleSummaryCard.kt:214` and as `summaryError`). Standardise on one
  `ErrorCard(message, onRetry, onDismiss)` component.
- **No offline detection.** Requests fire regardless of connectivity, wait out three
  backoff rounds, then surface a generic message. Check `NetworkCapabilities` first and
  fail fast with an actionable message.

## 3. Backend Review (client-side service layer)

There is no server. This section covers the network/data layer, which carries the
responsibilities a backend normally would — and therein lies the central architectural
problem (§4.1).

### 3.1 🔴 CRITICAL — API keys are embedded in the shipped APK

**Where:** `app/build.gradle.kts:32-56`, `ui/EnglishLearningApp.kt:285-286`,
`ui/tts/ArticleSpeaker.kt:17-19`

```kotlin
buildConfigField("String", "OPENROUTER_API_KEY",
    (localProperties.getProperty("openrouter.api.key") ?: "").asBuildConfigString())
```

`buildConfigField` generates `public static final String OPENROUTER_API_KEY = "sk-or-…"`.
`final String` constants are inlined into the DEX constant pool. `strings classes.dex |
grep sk-or-` recovers the key in seconds — no reverse engineering skill required.
`isMinifyEnabled = false` (`build.gradle.kts:60`) means there is not even obfuscation
noise to sift through.

**Impact:** Anyone who installs the APK can extract both keys and spend against your
OpenRouter and Deepgram accounts without limit. There is no per-user quota, no rate
limit, no revocation path short of rotating the key and shipping a new build. The README
says "Do not commit real API keys" — true, and irrelevant: the key is in the *artifact*,
not the repo.

**This is only acceptable under the PRD's "personal use, sideloaded, never distributed"
constraint.** The moment the README's framing applies, this is a hard blocker.

**Fix (correct):** Put a thin proxy between the app and both providers.

```
Android app → your backend (auth + quota + key custody) → OpenRouter / Deepgram
```

The backend holds the provider keys, authenticates the device (Play Integrity, Firebase
Auth anonymous, or a signed device token), enforces per-user rate limits and a monthly
spend cap, and forwards. A Cloudflare Worker or a single Cloud Run container is enough:

```ts
// worker.ts — ~30 lines is genuinely sufficient
export default {
  async fetch(req: Request, env: Env) {
    const user = await verifyAppToken(req.headers.get("Authorization"), env);
    if (!user) return new Response("unauthorized", { status: 401 });
    if (!(await withinQuota(user, env))) return new Response("quota exceeded", { status: 429 });
    return fetch("https://openrouter.ai/api/v1/chat/completions", {
      method: "POST",
      headers: { Authorization: `Bearer ${env.OPENROUTER_KEY}`, "Content-Type": "application/json" },
      body: req.body,
    });
  },
};
```

**Fix (interim, if a backend is genuinely out of scope):** Accept that this is a personal
build, and (a) set a hard monthly spend limit in the OpenRouter and Deepgram dashboards,
(b) enable `isMinifyEnabled = true`, and (c) state plainly in the README that the APK
must not be distributed.

### 3.2 🔴 CRITICAL — Duplicate rows in `recent_articles` on every summary

**Where:** `data/local/RecentArticleDao.kt:13-14`, `data/local/RoomArticleLocalStore.kt:31-38`,
`ui/EnglishLearningViewModel.kt:201, 287, 474`

```kotlin
@Insert                                              // OnConflictStrategy.ABORT
suspend fun insert(article: RecentArticleEntity): Long
```

`RecentArticleEntity.id` is `@PrimaryKey(autoGenerate = true) val id: Long = 0`. Passing
`0` makes SQLite assign a fresh rowid — there is no conflict to resolve, so every call
inserts a **new row**.

`saveRecentArticle` is called from three places, including
`requestArticleContext` (`:287`), which fires after the user taps "Get article context".

**Reproduction:**
1. Paste an article → cleaned and saved. → **row 1** (no summary)
2. Tap "Get article context" → saved again with the summary. → **row 2** (duplicate body)
3. Open row 1 from Recents, tap context again. → **row 3**

**Impact:** History fills with near-identical entries, each storing a full article body.
Users cannot tell them apart (`RecentArticleCard` shows title + a 160-char preview, which
are identical). There is also **no delete query in `RecentArticleDao` at all** — the user
has no way to clean this up. Combined with §3.3 this is unbounded, unmanageable growth of
the largest column in the database.

**Fix:** Give articles a stable identity and upsert on it.

```kotlin
@Entity(
    tableName = "recent_articles",
    indices = [Index(value = ["contentHash"], unique = true), Index(value = ["savedAtMillis"])]
)
data class RecentArticleEntity(
    @PrimaryKey(autoGenerate = true) val id: Long = 0,
    val contentHash: String,          // sha256(title + cleanArticle)
    /* … */
)

@Dao
interface RecentArticleDao {
    @Query("SELECT * FROM recent_articles ORDER BY savedAtMillis DESC LIMIT :limit")
    fun observeRecent(limit: Int = 100): Flow<List<RecentArticleEntity>>

    @Query("SELECT id FROM recent_articles WHERE contentHash = :hash LIMIT 1")
    suspend fun findIdByHash(hash: String): Long?

    @Upsert suspend fun upsert(article: RecentArticleEntity): Long

    @Query("DELETE FROM recent_articles WHERE savedKey = :id")
    suspend fun delete(id: Long)

    @Query("DELETE FROM recent_articles WHERE id NOT IN " +
           "(SELECT id FROM recent_articles ORDER BY savedAtMillis DESC LIMIT :keep)")
    suspend fun trimTo(keep: Int)
}
```

Then in the store: look up by hash, reuse the id if present, upsert. Call `trimTo(200)`
after each save.

### 3.3 🟠 HIGH — Unbounded growth in `cached_meanings` and the Deepgram disk cache

**`cached_meanings`** (`data/local/MeaningEntity.kt:57-63`): the primary key is
`"${mode}|${word}|${fullSentence}"` — full sentence text, verbatim. Every distinct
sentence a word appears in creates a new row storing seven text fields. There is **no
eviction query, no TTL, no size cap**, and `savedAtMillis` is stored but never read.

**Deepgram cache** (`ui/tts/DeepgramTextToSpeech.kt:52`): `pruneCache()` is called

past `MAX_CACHE_BYTES` (200 MB). Listening to several long articles back-to-back with no
process restart fills the device.

**Impact:** Steady, invisible storage growth. On a low-storage device this surfaces as
"ArthaReader is using 1.2 GB" in Settings, which is how apps get uninstalled.

**Fix:**

```kotlin

@Query("DELETE FROM cached_meanings WHERE cacheKey NOT IN " +
       "(SELECT cacheKey FROM cached_meanings ORDER BY savedAtMillis DESC LIMIT :keep)")
suspend fun trimTo(keep: Int)
```

```kotlin
// DeepgramTextToSpeech — prune after every article, not once per process
activeJob = scope.launch {
    try { /* … existing synthesis + playback … */ }
    finally {
        onWordIndex(null); onComplete()

}
```

Also cap it far lower — 200 MB of MP3 for a reading app is excessive; 50 MB is generous.

### 3.4 🟠 HIGH — Per-tap LLM cost is multiplied by 6 and scales with article length

**Where:** `ui/EnglishLearningViewModel.kt:329`, `data/OpenRouterArticleService.kt:255-282`,
`data/NetworkRetry.kt:22`

```kotlin
// ViewModel — passes the ENTIRE article as context, every tap
articleService.fetchMeaning(articleText = currentArticle.contextForMeaning(), …)

// CleanArticleResult.kt:14-18 — contextForMeaning() is title + subtitle + author + date + full body
```

`fetchMeaning` makes a first request; if `isValidFor` fails it makes a **second, corrective
request**. Each `sendJsonChatRequest` is wrapped in `retryWithBackoff(maxAttempts = 3)`.

**Worst case per single word tap: 6 requests, each carrying the full article.**

For a 1,200-word article that is roughly 1,700 input tokens × 6 = ~10,000 tokens for one
tap. A user reading one article and tapping 30 words could burn 300k tokens.

**Impact:** Cost that scales as O(article_length × taps), latency of several seconds per
tap even on the happy path, and — combined with §3.1 — a bill anyone can run up.

**Fix (three compounding wins):**

1. **Send a context window, not the article.** The model needs the tapped sentence plus
   surrounding sentences, not paragraph 47.

```kotlin
fun CleanArticleResult.contextForMeaning(around: String, radiusChars: Int = 800): String {
    val idx = cleanArticle.indexOf(around).takeIf { it >= 0 } ?: 0
    val from = (idx - radiusChars).coerceAtLeast(0)
    val to   = (idx + around.length + radiusChars).coerceAtMost(cleanArticle.length)
    return listOf(title, subtitle).filter { it.isNotBlank() }
        .plus(cleanArticle.substring(from, to)).joinToString("\n\n")
}
```
   ~90% token reduction on long articles, with no quality loss for a contextual lookup.

2. **Do not retry the corrective request.** The retry is for *transient network* failures;
   a wrong-script response is not transient. Wrap only the first attempt.

3. **Cache the raw response, not just the validated one.** Currently a response that
   fails `hasValidKannadaFields()` is discarded and the whole flow reruns from scratch on
   the next tap of the same word.

### 3.5 🟠 HIGH — Article cleaning asks the LLM to echo the entire body verbatim

**Where:** `data/OpenRouterArticleService.kt:26-94`

```
- cleanArticle must contain the COMPLETE article body, not a shortened version
- Every sentence in cleanArticle must exist verbatim in the raw text
- Never return the article body as a single paragraph
```

**Why it's a problem:** Output tokens are typically 3–4× the price of input tokens, and
this prompt makes output ≈ input. It is also the slowest and least reliable possible way
to strip boilerplate: LLMs truncate long outputs, paraphrase under instruction pressure,
and hit `max_tokens` silently.

The codebase already knows this. `CleanArticleResult.withLocalArticleFallback` +
`looksSummarizedComparedTo` exist purely to detect when the model summarised instead of
extracting, and fall back to `ArticleFormatter` — a **407-line local heuristic cleaner
that already works**:

```kotlin
// CleanArticleResult.kt:20-28
fun looksSummarizedComparedTo(rawText: String): Boolean {
    …
    return cleanWordCount < localArticleEstimateWordCount * 0.12
}
```

**Fix — invert the relationship.** Run `ArticleFormatter.format()` first; it is free,
instant, and offline. Use the LLM only for the metadata the heuristic cannot infer:

```kotlin
override suspend fun cleanArticle(rawText: String): CleanArticleResult {
    val body = withContext(Dispatchers.Default) { ArticleFormatter.format(rawText) }
    // Only ask the model for title/subtitle/author/date, from the first ~1500 chars.
    val meta = sendJsonChatRequest(
        systemMessage = "Extract article metadata. Return only valid JSON.",
        userMessage = """
            Return {"title":"","subtitle":"","author":"","publishedDate":""} for this article opening.
            Use empty strings for anything not present. Do not invent values.

            ${body.take(1500)}
        """.trimIndent()
    )
    return CleanArticleResult.fromJson(JSONObject(meta)).copy(cleanArticle = body)
}
```

This cuts the most expensive call in the app to a fraction of its size, makes it
resilient (a metadata failure degrades to an untitled article rather than no article),
and removes the summarisation-detection machinery entirely.

### 3.6 🟠 HIGH — Malformed model output surfaces a raw `JSONException` to the user

**Where:** `data/OpenRouterArticleService.kt:91, 143, 193, 246, 326`

```kotlin
val result = CleanArticleResult.fromJson(JSONObject(content))   // ← outside the try
```

`sendJsonChatRequest` wraps network failures in a friendly `IllegalStateException`
(`:393-402`). But `JSONObject(content)` is called by each *caller*, outside that
protection. When the model returns prose, a markdown fence variant, or a truncated
object, `org.json` throws:

```
org.json.JSONException: Value Sure of type java.lang.String cannot be converted to JSONObject
```

which flows to `EnglishLearningViewModel.kt:423` → `error.message` → straight into the
UI error card.

**Fix:** Parse inside the service boundary and map to a domain error.

```kotlin
private inline fun <T> parseJson(content: String, block: (JSONObject) -> T): T =
    try { block(JSONObject(content)) }
    catch (e: JSONException) {
        Log.w(TAG, "Unparseable model response: ${content.take(200)}", e)
        throw IllegalStateException("The article service returned an unexpected response. Please try again.", e)
    }
```

More robustly, define a sealed `ServiceError` hierarchy (`Network`, `RateLimited`,
`Unauthorized`, `MalformedResponse`, `Unknown`) so the UI can decide whether to show
Retry, and stop using `Throwable.message` as a user-facing string channel.

### 3.7 🟡 MEDIUM — Hand-rolled `HttpURLConnection` in three places

**Where:** `OpenRouterArticleService.kt:405-451`, `YouTubeTranscriptService.kt:234-283`,

### 3.8 🟡 MEDIUM — Non-idempotent POSTs retried on generic `IOException`

**Where:** `data/NetworkRetry.kt:15, 22-45`

```kotlin
fun Throwable.isTransientNetworkError(): Boolean = this is IOException
```

A `SocketTimeoutException` on `readTimeout` means the request *reached* OpenRouter and
was likely processed and billed — the response just didn't arrive in time. Retrying
charges again. Same for Deepgram synthesis.

**Fix:** Distinguish connect-phase failures (safe to retry) from read-phase ones:

```kotlin
fun Throwable.isRetryable(): Boolean = when (this) {
    is RetryableHttpException -> true                     // explicit 429 / 5xx
    is SocketTimeoutException -> false                    // may already be billed
    is java.net.ConnectException, is java.net.UnknownHostException -> true
    else -> false
}
```

Two smaller issues in the same file:
- `lastError` (`:31, 39`) is assigned but the `throw lastError` at `:44` is unreachable —
  the loop always either returns or throws. Delete the variable.
- No jitter. Three clients hitting a 429 simultaneously retry in lockstep. Add
  `+ Random.nextLong(currentDelay / 4)`.

## 4. Architecture Review

### 4.1 Does the current architecture scale?

**Structurally: partly. Economically: no.**

The layering (`ui` → `domain` ← `data`) is correct for an app of this size, and the
`ArticleAiService` / `ArticleLocalStore` seams mean the Compose layer is genuinely
decoupled from OpenRouter and Room. That will hold to maybe 3–5× the current size.

What does not scale is **the decision to have no server** (PRD §Architecture: "Android
App → OpenRouter API. No backend (personal use only)"). That single choice cascades into:

- keys in the client (§3.1),
- no rate limiting, no quota, no abuse control,
- prompts unchangeable without a Play Store release,
- model choice frozen at build time (`BuildConfig.OPENROUTER_MODEL`),
- no shared meaning cache — every user pays to look up "ubiquitous" for the first time,
- no analytics on which words users tap, which is the most valuable data this app
  generates.

For the PRD's single user that is a sound trade. For the README's product it is the
architecture's ceiling. A ~200-line proxy removes all seven constraints at once, and
makes a server-side meaning cache possible — which for a vocabulary app would cut LLM
spend by an order of magnitude, since word+context lookups repeat heavily across users.

**Module structure** will also bite. Everything is in `:app`. At ~9k LOC that is fine;
past ~15k, incremental builds degrade and layer violations become unenforceable. When you
split, split by layer first (`:core:domain`, `:core:data`, `:core:ui`, `:feature:reader`,
`:feature:practice`) — the package boundaries are already clean enough that this is
mostly file moves.

### 4.2 Unnecessary complexity to remove

**Delete outright (~200 lines of dead code):**

| Symbol | Location | Note |
|---|---|---|
| `ArticleAiService.formatTranscript` + impl | `ArticleAiService.kt:6`, `OpenRouterArticleService.kt:96-152` | 57 lines. Never called — README confirms captions are imported without AI rewrite. |
| `SavedWordEntity.fromSavedWord` | `SavedWordEntity.kt:53-71` | No callers. |
| `rememberArticleTextToSpeech` | `ArticleTextToSpeech.kt:135-142` | Superseded by `rememberArticleSpeaker`. |
| `ArticleSpeaker.isArticleSpeaking` | `ArticleSpeaker.kt:32-34` | No callers. |
| `DeepgramTextToSpeech.isPaused` / `.isActive` | `DeepgramTextToSpeech.kt:58-62` | No callers. |
| `alignSttWithSource` | `DeepgramTextToSpeech.kt:561-564` | Thin wrapper; only the test calls it. Point the test at `alignSttWithSourceVerbose`. |
| `firstFullyVisibleParagraphIndex` | `ArticleViewerScreen.kt:510-514` | Already `@Suppress("unused")` — a marker that someone knew. |
| `Modifier.interactiveWordUnderline` | `ArticleChrome.kt:258-261` | Returns `this` in both branches. |
| `String.isLikelyHeading` | `TextAnalysis.kt:105-113` | Production callers: zero. Only `TextAnalysisTest` uses it — a test testing dead code. |
| 7 unused drawables | `ic_globe`, `ic_languages`, `ic_menu`, `ic_search`, `ic_stop_circle`, + 2 launcher assets | |

**Genuinely over-engineered:**

- **`TextAnalysis.kt`'s phrase heuristics** (`:115-335`). Three hardcoded word lists —
  `phraseModifiers` contains `"wall"`, `"street"`, `"asian"`, `"equity"`;
  `phraseHeads` contains `"nifty"`-adjacent finance terms like `"indices"`,
  `"conglomerates"`, `"volatility"`, `"portfolio"`. This is a bespoke NLP engine tuned to
  Indian financial news that will silently produce nonsense phrase groupings on a sports
  report or a science article, and it is 220 lines to maintain.
  The app **already** gets high-quality phrases from
  `ArticleAiService.extractIdiomaticPhrases`, which are passed in as `priorityPhrases`.
  **Delete the heuristic entirely and rely on the LLM-detected phrases**, defaulting to
  single-word tokens otherwise. That removes 220 lines and makes behaviour predictable
  and domain-independent.
- **The Deepgram STT round-trip** (`DeepgramTextToSpeech.kt:250-282`). To highlight words
  during playback, every synthesised MP3 is uploaded *back* to Deepgram's `/listen` for
  forced alignment, then reconciled by a 50-line greedy matcher
  (`alignSttWithSourceVerbose`). That doubles the API cost and roughly doubles
  time-to-first-audio on a cache miss, to power a cosmetic feature. The
  `estimatedWordStartsForDuration` fallback (character-proportional distribution) already
  exists and is adequate. **Recommendation: make STT alignment opt-in behind a setting,
  defaulting to the estimate.** If precision matters, Deepgram Aura's WebSocket API
  returns timing metadata natively — one call instead of two.

### 4.3 Separation of concerns

**Good:** `domain` has zero Android imports. `ui.state` is separate from `domain`. DAOs
are thin. Entity↔domain mapping lives on the entities.

**Violations:**

1. **DI happens inside composables.** `EnglishLearningApp.kt:283-303`:
   ```kotlin
   @Composable private fun rememberDefaultArticleService(): ArticleAiService =
       remember { OpenRouterArticleService(BuildConfig.OPENROUTER_API_KEY, …) }
   ```
   The composition layer constructs network clients and opens the database. This makes
   the whole graph untestable from a Compose test and couples UI to `BuildConfig`.

2. **`YouTubeTranscriptService` is not injectable.**
   `EnglishLearningViewModel.kt:52` defaults it inline:
   ```kotlin
   private val youTubeTranscriptService: YouTubeTranscriptService = YouTubeTranscriptService()
   ```
   `EnglishLearningViewModelFactory` never passes one. There is no way to test the
   YouTube import path without real network. It should also be behind an interface, like
   its two siblings.

3. **`OpenRouterArticleService` has five responsibilities** in 478 lines: prompt
   authoring, HTTP transport, JSON parsing, response validation
   (`isValidFor`, `isValidDetectedPhrase`), and post-processing
   (`ArticleFormatter.postClean`). Split:
   ```
   data/ai/OpenRouterClient.kt        // transport only: payload in, content string out
   data/ai/Prompts.kt                 // prompt templates, versioned
   data/ai/ArticleAiServiceImpl.kt    // orchestration + parsing + validation
   ```

4. **`ArticleViewerScreen` reads `SharedPreferences` directly** (`:127-138`) — a
   persistence concern in a screen.

### 4.4 Patterns to introduce / remove

**Introduce:**

- **A DI framework.** Hilt is the obvious choice for Android; `hilt-navigation-compose`
  removes the manual `ViewModelProviderFactory` and the composable-side construction in
  one step.
  ```kotlin
  @HiltViewModel
  class EnglishLearningViewModel @Inject constructor(
      private val articleService: ArticleAiService,
      private val localStore: ArticleLocalStore,
      private val youTubeService: YouTubeTranscriptService,
  ) : ViewModel()
  ```
- **A repository layer between ViewModel and services.** The ViewModel currently
  orchestrates cache-check → network → cache-write → state-update inline
  (`:306-353`). That logic belongs in an `ArticleRepository` / `MeaningRepository`;
  the ViewModel should only map results to UI state.
- **A sealed `AppError` type**, replacing `Throwable.message` as the user-facing string
  channel (§3.6).
- **Use cases** for the two multi-step flows (`ImportYouTubeArticleUseCase`,
  `CleanAndSaveArticleUseCase`) — these are the ~60-line duplicated blocks noted in §6.1.

**Remove:**

- The bespoke phrase-detection heuristic (§4.2).
- The manual `ViewModelProvider.Factory` (replaced by Hilt).
- `String.hasKannadaScript()` / `hasNonKannadaIndicScript()` as a *retry trigger* — keep
  them as a quality signal, but do not spend a second full LLM round-trip on them (§3.4).

## 6. Refactoring Opportunities

### 6.1 Duplicated logic

**(a) The article-ingest tail, duplicated verbatim.**
`EnglishLearningViewModel.kt:178-201` (YouTube) and `:451-474` (paste) are the same 24
lines: extract idiomatic phrases → merge → conditionally update state → save. Extract:

```kotlin
private suspend fun enrichAndPersist(article: CleanArticleResult) {
    val phrases = try {
        articleService.extractIdiomaticPhrases(article.cleanArticle)
    } catch (e: CancellationException) { throw e } catch (_: Throwable) { emptyList() }

    val enriched = if (phrases.isEmpty()) article else article.copy(idiomaticPhrases = phrases)
    if (phrases.isNotEmpty()) {
        _uiState.update { s ->
            if (s.cleanedArticle?.cleanArticle == article.cleanArticle)
                s.copy(cleanedArticle = enriched) else s
        }
    }
    runCatching { localStore.saveRecentArticle(enriched) }
}
```

**(b) `createMeaningCacheKey` and `createSavedWordKey` are byte-identical.**
`MeaningEntity.kt:57-63` and `SavedWord.kt:19-25` both compute
`"${mode.name.lowercase()}|${word.trim().lowercase()}|${sentence.trim()}"`. They will
drift. Unify in `domain`:

```kotlin
// domain/LookupKey.kt
fun lookupKey(word: String, sentence: String, mode: MeaningLookupMode): String =
    "${mode.name.lowercase()}|${word.trim().lowercase()}|${sentence.trim().hashCode()}"
```
(Hashing the sentence also fixes the unbounded-key-size issue from §3.3.)

**(c) Three copies of HTTP boilerplate** — §3.7.

**(d) Two `unwantedLinePhrases`-style filter lists.** `ArticleFormatter`'s 130-entry
`unwantedLinePhrases` + 48-entry `unwantedShortLines` are also expressed, in prose, in
the `cleanArticle` LLM prompt (`OpenRouterArticleService.kt:44-66`). Two encodings of the
same rules. §3.5's restructure eliminates the prompt copy.

**(e) `androidx.compose.foundation.layout.Spacer(...)` fully qualified twice**
(`MeaningSheet.kt:492, 520`) — plus a hand-rolled `Box(Modifier.height(4.dp).width(1.dp))`
in `ArticleSummaryCard.kt:279` where a `Spacer` belongs.

## 7. Performance

### 7.1 Expensive operations, ranked

| Operation | Cost | Location | Fix |
|---|---|---|---|
| Full article → LLM per word tap, ×2 attempts, ×3 retries | **Seconds of latency + ~10k tokens per tap** | `EnglishLearningViewModel.kt:329` | Context window (§3.4) |
| LLM echoing the whole article body for cleaning | Output tokens ≈ input tokens; 5–15 s | `OpenRouterArticleService.kt:26` | Local-first extraction (§3.5) |
| Deepgram STT round-trip per chunk | 2× API cost, 2× time-to-first-audio | `DeepgramTextToSpeech.kt:250` | Make opt-in (§4.2) |
| `AnnotatedString` rebuild for all N paragraphs per lookup | O(N × tokens) per tap | `ArticleViewerScreen.kt:422` | Per-paragraph keying (§2.8) |
| Word count regex-split per keystroke | O(article length) per character | `ArticleInputScreen.kt:248` | `derivedStateOf` + debounce (§2.7) |
| `SELECT *` loading all article bodies for the Recents list | O(total corpus) per emission | `RecentArticleDao.kt:10` | Projection DTO (§3.10) |
| `toWordTokens()` allocating a substring per token | ~1 allocation per word | `TextAnalysis.kt:48-62` | Track `lastEnd` with `indexOf('\n', lastEnd)` instead of `substring().contains()` |

### 7.2 Unnecessary re-renders

Already handled well: the active-paragraph-only `currentWordIndex` (`:249`), the
`lookedUpSnapshot` keyed on set size (`:125`), and `produceState` for off-main-thread
tokenisation (`:93-118`). Credit where due.

Remaining:
- Every keystroke in the paste field emits a new `EnglishLearningUiState`, which the
  reader route also observes (§2.12).
- `animateFloatAsState` on `readingProgress` (`:157`) recomposes the progress bar on every
  scroll frame — acceptable, but `graphicsLayer`-based drawing would avoid layout.
- `LaunchedEffect(effectiveWordIndex, paragraphs)` (`:163`) restarts on **every word
  index change** during playback — ~25×/sec at `WORD_TICK_MS = 40`. Each restart walks
  `paragraphWordOffsets` and `visibleItemsInfo`. Key it on the *paragraph* index instead:
  ```kotlin
  LaunchedEffect(activeParagraphIndex) { /* scroll if not visible */ }
  ```
  This is a real win — it cuts the effect restarts by ~50×.

### 7.3 Redundant API calls

- `setLookupMode` (`:366-370`) re-invokes `selectWord`, which re-checks cache then
  re-fetches. Fetching both Word and Sentence modes in one request (the prompt already
  asks for all seven fields) would halve calls for users who toggle.
- `requestArticleContext` guards on `summary != null` — good. But `openRecentArticle`
  restores a summary from the DB, so the guard works there too. Correct.
- No request coalescing: rapid taps on different words fire concurrent requests; only the
  latest is retained (`updateMeaningIfStillSelected`), but all are paid for.
  `meaningLookupJob?.cancel()` does cancel, but a cancelled coroutine does not cancel an
  in-flight `HttpURLConnection` — the request completes server-side and is billed.
  **OkHttp with `call.cancel()` would actually abort it.** Another argument for §3.7.

### 7.4 Memory

- `MediaPlayer` lifecycle in `playFile` (`:284-350`) is careful — `invokeOnCancellation`
  releases, and the `finally` guards with `player === mediaPlayer`. Good.
  But `player` is a plain `var` read from `pause()`/`resume()` on the caller's thread and
  written from `Dispatchers.Main`. Mark it `@Volatile` alongside `paused`.
- `speak()` launches an `async` for **every** chunk up front (`:105-107`). A 100k-char
  article is ~56 chunks → 56 coroutines and 56 `Deferred<SynthesizedChunk>` held until
  awaited, each holding a `File` handle reference. Bound it — process in windows of ~8.
- A race in `stop()` → `speak()`: `stop()` cancels `activeJob`, whose `finally`
  (`:128-131`) calls `onComplete()` → `_playbackState.value = Idle`. If the new `speak()`
  has already set `Playing`, the old job's `finally` can land afterwards and reset it to
  `Idle` while audio plays. Guard with a generation counter:
  ```kotlin
  private var generation = 0
  fun speak(...) {
      val gen = ++generation
      stop()
      activeJob = scope.launch {
          try { /* … */ } finally {
              if (gen == generation) { onWordIndex(null); onComplete() }
          }
      }
  }
  ```

on rotation are bugs regardless of audience. Production readiness under the PRD's
constraints would be **5/10** rather than 2/10, and the Critical list shrinks to C1–C4.

## Closing note

The instinct-level engineering here is better than the score suggests. The domain layer
is clean, the coroutine discipline is genuinely good, the Deepgram pipelining is
sophisticated, and the recomposition scoping in the reader shows someone who understands
Compose. Those are the hard things.

What's missing is the boring infrastructure that catches the easy things: a CI job would
have blocked both build-breaking commits before they reached `main`; a lint rule would
have caught the dead code; a code review would have caught "40% read". The gap between
this codebase and a production one is mostly process, not skill — which is the good kind
of gap to have.

Start with §10.1. C1–C4 are under two hours combined and take the project from
"doesn't build" to "shippable to yourself".
